World readiness must be evaluated from observable continuity and bounded effects, not from document volume, connected tools, named stages, repository structure, model count, or roadmap completion.

## Readiness dimensions
A bounded world/capability slice is stronger when it can demonstrate:
- stable identity across representation/carrier changes;
- lawful source and authority resolution;
- dependency and affected-scope visibility;
- evidence-backed state transitions;
- failure/hold/invalidation visibility;
- receiver-owned return and reconciliation;
- reconstruction from last-valid state plus accepted deltas/evidence;
- replacement or loss of a carrier without creating a second truth;
- purpose-fit Human / Professional / Machine representations that back-map to the same existence;
- repeated retest showing behavior/effect, not only written architecture.

## Prohibited readiness inflation
Do not infer readiness from:
- GitHub being durable;
- a branch, register, corpus database, scheduler or workflow existing;
- fixed window/topology definitions;
- a model being `on-chain`;
- ecosystem connectors being installed;
- a public interface rendering successfully;
- a Return packet being written;
- a checklist or milestone document being complete.

`Architecture described != World executable`
`BuildReady != Runtime`
`Return written != Receiver absorbed`
`Connected ecosystem != Operational field`
`Self-described stage != Proven maturity`
