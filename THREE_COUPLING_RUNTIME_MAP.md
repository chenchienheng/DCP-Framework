# Continuity Coupling Contract

> Lifecycle: `PUBLIC_RESEARCH_REFERENCE`
> Runtime: `false`
> Native source root: `false`
> Authority: `none`

This document preserves the minimal coupling primitives required for reconstructable multi-carrier continuity. It does not establish a fixed runtime topology, sovereign platform, permanent central node, or mandatory window count.

## 1. Core rule
A coherent system may span many carriers without becoming many independent truths.

Continuity requires that material change remain:
- identifiable;
- dependency-aware;
- evidence-linked;
- returnable;
- reconstructable.

`Many carriers != many authorities`
`Repository durability != Native Source`
`Visibility != Current`
`Return packet != Closeout`

## 2. Coupling primitives

### Dependency coupling
Preserves what depends on what, including source identity, constraints, prerequisites, receiver, and affected scope.

### Change / event coupling
Preserves material transitions: trigger, delta, before/after relation, affected state, evidence, hold/invalidation, and action authority.

### Return / rebuild coupling
Preserves what useful delta returned, where it returned, whether it was reconciled/admitted, and how the last valid state can be rebuilt without depending on one volatile session or carrier.

These are functional relations, not sovereign layers.

## 3. Stable identity and replaceable carriers
A carrier may change while the governed object remains the same. Migration must preserve stable identity, source authority, evidence, dependency edges, action boundaries, and ordered return/rebuild semantics.

Examples of carriers may include repositories, drives, documents, databases, workflow tools, model surfaces, calendars, or human review. No carrier becomes the task, identity, or authority merely because it stores durable material.

## 4. Gate-bound transition
A material transition should resolve at least:
- source and source authority;
- current state/evidence;
- dependency impact;
- rights/privacy boundary where applicable;
- action authority;
- expected effect;
- return target;
- reconciliation/admission requirement;
- rebuild/re-entry evidence.

## 5. Incompleteness and drift
Construction incompleteness is not the same as drift. Incompleteness may remain explicit as Candidate / Pending / To Verify. Drift occurs when an old representation silently becomes Current, a carrier is mistaken for authority, a transition loses evidence, or return/rebuild becomes impossible.

## 6. World executability implication
A document corpus becomes closer to an executable world when state and transitions can be instantiated from stable identity + dependencies + evidence + authority + gates + effects + return/rebuild, rather than from prose order or folder location.
