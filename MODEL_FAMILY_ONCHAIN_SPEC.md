This file preserves lessons from an earlier attempt to make model participation auditable and returnable. The useful idea survives; the fixed `on-chain / owner_window / writeback register / return_to_00` topology does not.

## Retained primitives
A material model operation should resolve, as needed:
- model/capability identity and revision;
- receiver or accountable owner;
- lawful source references and source authority;
- allowed scope and rights/privacy boundary;
- expected output and claim ceiling;
- evidence/provenance and contradiction visibility;
- proposed action versus actual action authority;
- return target and receiver-owned reconciliation;
- rebuild/re-entry evidence where material.

Model families may differ in strengths, failure modes, modality, cost, latency, context, extraction, synthesis or domain fit. These are capability characteristics, not permanent system roles.

## Retired assumptions
- every model must belong to a fixed runtime window;
- a model becomes system-valid by being `on-chain`;
- repository/writeback/register placement establishes model membership or authority;
- disagreement must escalate to `00`;
- one main model chain or fixed family-role table is required;
- more registered models means greater system maturity.

## Current rule
`Model capability != Authority`
`Invocation != Admission`
`Output != Receiver absorption`
`Model family label != Permanent role`
`Connected model != Runtime member`
