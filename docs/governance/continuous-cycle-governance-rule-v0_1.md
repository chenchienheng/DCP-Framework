# Continuous Cycle Governance Rule v0.1

Status: Candidate / Governance Rule / No Runtime / No External Writeback
Use As: QHA rule for treating cleanup, database, workflow, field proof, and repository alignment as continuous cycles rather than one-time tasks
Do Not Use As: approved doctrine, runtime automation, company policy, or closeout

## Core

XuanLing work is not cleaned once and finished. A living chain requires recurring intake, classification, evidence, return, feedback, and rebuild. The same applies to databases, repositories, M365 workflow models, field proof cards, and human work patterns.

## Continuous Loop

```yaml
Continuous_Governance_Loop:
  Intake:
    meaning: "new signal, file, case, return, task, or external input arrives"
  Classify:
    meaning: "Signal Intake Gate / authority ring / carrier fit"
  Build_or_Record:
    meaning: "bounded build card, evidence record, or candidate document"
  Evidence:
    meaning: "proof of what was actually created, tested, or observed"
  Return_Check:
    meaning: "verification of closure criteria and remaining gaps"
  Feedback:
    meaning: "what must change in schema, gate, card, route, or wording"
  Rebuild:
    meaning: "next iteration, archive, supersede, or upgrade"
```

## M365 Landing Pattern

```yaml
Minimal_Landing_Pattern:
  principle:
    - "do not keep expanding blueprint"
    - "build the smallest verifiable loop"
    - "record evidence"
    - "run return check"
    - "only then improve"
  key_rules:
    - "No Build Card = Reference Only"
    - "No Evidence Record = Not Completed"
    - "No Return Check = Not Closed"
```

## Human Pattern Boundary

Human work also has recurring loops: intake, interpretation, action, evidence, rest, return, and revision. QHA must not force one-time closure when the nature of the work is cyclical.

## Red Doors

- Cleanup Once != Governance.
- Build Once != System.
- Evidence Missing != Completed.
- Return Check Missing != Closed.
- Database Row != OCF Cell.
- More Blueprint != More Progress.
- Continuous Cycle != Runtime Automation.

## Final Rule

QHA should prefer small verifiable loops over large explanatory blueprints. A chain becomes real by repeated evidence and return, not by one-time documentation.
